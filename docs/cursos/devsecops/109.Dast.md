# DAST, atacar tu propia aplicación

Hasta ahora hemos analizado ficheros: código, dependencias, imágenes, Terraform. **DAST** (*Dynamic Application Security Testing*) hace lo contrario: ignora el código y ataca la aplicación en marcha, como haría alguien de fuera.

Es la diferencia entre revisar los planos de un edificio y probar si las puertas están cerradas.

## Por qué hacen falta los dos

Cada enfoque ve cosas que el otro no puede ver:

| | SAST (capítulo 4) | DAST |
|---|---|---|
| **Necesita** | El código | La aplicación desplegada |
| **Cuándo** | En cada push | Sobre un entorno real |
| **Velocidad** | Segundos | Minutos |
| **Ve** | Todas las rutas del código | Solo lo que consigue alcanzar |
| **Falsos positivos** | Bastantes | Pocos: lo ha reproducido |
| **Se le escapa** | Errores de configuración y de despliegue | Código que no llega a ejecutar |

El punto clave está en la penúltima fila. Un SAST te dice *"esta línea parece peligrosa"*. Un DAST te dice *"he mandado esto y ha pasado esto"*. Por eso sus hallazgos cuestan mucho menos de discutir.

Y lo de la última fila es lo importante: un DAST detecta que **falta la cabecera `Content-Security-Policy`**, algo que no está escrito en ninguna línea de código y que ningún analizador estático puede ver.

## Laboratorio: preparar el objetivo

Necesitamos la aplicación corriendo. Para que funcione igual en macOS, Linux y Windows, la levantamos en una red de Docker y lanzamos ZAP en la misma red:

```bash
cd devsecops-demo
docker build -t devsecops-demo:1.1 .

docker network create devsecops-lab
docker run -d --rm --name demo-app --network devsecops-lab devsecops-demo:1.1
```

:::tip Por qué una red de Docker y no `localhost`

`--network host` se comporta distinto en macOS y en Windows, y `localhost` dentro de un contenedor es el propio contenedor, no tu máquina. Poniendo ambos en la misma red de Docker se llaman por su nombre (`demo-app`) y el laboratorio funciona igual en cualquier sistema.

:::

## Escaneo pasivo

`zap-baseline.py` navega la aplicación y **observa** el tráfico sin atacar. Es rápido, no rompe nada y es lo que puedes permitirte ejecutar en cada despliegue.

```bash
docker run --rm --network devsecops-lab \
  zaproxy/zap-stable zap-baseline.py -t http://demo-app:3000
```

Salida real, en poco más de un minuto:

```
Total of 9 URLs
WARN-NEW: Missing Anti-clickjacking Header [10020] x 2
WARN-NEW: X-Content-Type-Options Header Missing [10021] x 5
WARN-NEW: Server Leaks Information via "X-Powered-By" HTTP Response Header [10037] x 5
WARN-NEW: Content Security Policy (CSP) Header Not Set [10038] x 2
WARN-NEW: Permissions Policy Header Not Set [10063] x 4
WARN-NEW: Application Error Disclosure [90022] x 1
FAIL-NEW: 0   WARN-NEW: 9   PASS: 58
```

Todo esto es invisible para un analizador estático, porque no son fallos de código sino **de configuración de las respuestas**:

- **CSP ausente**: nada limita qué scripts puede ejecutar el navegador
- **Anti-clickjacking ausente**: tu página se puede embeber en un iframe ajeno
- **`X-Powered-By`**: estás anunciando que corres Express, y con qué versión
- **Application Error Disclosure**: recuerda el `res.status(500).json({ error: err.message })` del capítulo 4 — está devolviendo el error interno al cliente

La mayoría se arreglan con una línea:

```javascript
const helmet = require('helmet');
app.use(helmet());
```

## Escaneo activo

`zap-full-scan.py` sí ataca: inyecta payloads en cada parámetro que encuentra.

```bash
docker run --rm --network devsecops-lab \
  zaproxy/zap-stable zap-full-scan.py -t http://demo-app:3000
```

Tarda bastante más, y encuentra lo que el pasivo no puede:

```
WARN-NEW: Cross Site Scripting (Reflected) [40012] x 1
WARN-NEW: Cross Site Scripting (DOM Based) [40026] x 3
FAIL-NEW: 0   WARN-NEW: 11   PASS: 130
```

Ahí está el XSS reflejado. Viene de esta línea de `src/vistas.js`:

```javascript
<p>Has buscado: ${busqueda}</p>   // ❌ sin escapar
```

Compruébalo tú mismo:

```bash
curl "http://localhost:3000/?q=<script>alert(1)</script>"
```

```html
<p>Has buscado: <script>alert(1)</script></p>
```

El navegador ejecutará ese script. Con un `<script>` que robe la cookie de sesión en vez de un `alert`, tienes el ataque completo.

:::danger Nunca lances un escaneo activo sin permiso

El escaneo activo **es un ataque**: manda payloads reales, puede crear registros basura, borrar datos o tumbar el servicio.

Lánzalo solo contra sistemas tuyos y en un entorno de pruebas. Contra un sistema ajeno sin autorización por escrito, es un delito.

:::

## En el pipeline

El patrón es: levantar la aplicación, escanearla, publicar el informe.

```yaml
# .github/workflows/dast.yml
name: DAST
on:
  schedule:
    - cron: '0 3 * * 1'   # los lunes de madrugada
  workflow_dispatch:

jobs:
  zap:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Levantar la aplicación
        run: |
          docker build -t demo:test .
          docker run -d --name demo-app -p 3000:3000 demo:test
          timeout 60 bash -c 'until curl -sf http://localhost:3000/health; do sleep 2; done'

      - name: Escaneo pasivo
        uses: zaproxy/action-baseline@v0.12.0
        with:
          target: 'http://localhost:3000'
          cmd_options: '-a'
```

Dos decisiones importantes en ese YAML:

**El escaneo pasivo puede ir en cada push. El activo, no.** Tarda demasiado y ataca de verdad. Va programado por la noche o a mano, contra un entorno de staging.

**Espera a que la aplicación responda.** Ese `until curl` evita el fallo más común: ZAP arrancando antes que la aplicación y reportando que no hay nada.

## Gestionar los avisos

El primer escaneo de una aplicación con años encima sale con decenas de avisos. Se gestiona con un fichero de reglas:

```
# .zap/rules.tsv
10015	IGNORE	(Re-examine Cache-control Directives)
10063	WARN	(Permissions Policy Header Not Set)
10038	FAIL	(Content Security Policy Header Not Set)
```

Tres niveles: `IGNORE` no aparece, `WARN` informa, `FAIL` rompe el build. Empieza casi todo en `WARN` y ve promocionando a `FAIL` lo que ya tengas resuelto — así el control sube de nivel sin bloquear a nadie.

## Más allá de ZAP

ZAP asume que hay páginas que navegar. Si lo tuyo es una API sin interfaz, el spider no encuentra nada y el escaneo sale vacío y engañosamente limpio.

En ese caso, dale la especificación de la API:

```bash
docker run --rm --network devsecops-lab zaproxy/zap-stable \
  zap-api-scan.py -t http://demo-app:3000/openapi.json -f openapi
```

Es un buen argumento para mantener el OpenAPI al día: además de documentar, es lo que permite escanear la API en serio.

## Resumen

- DAST ataca la aplicación en marcha: ve configuración y despliegue, no código
- Encuentra lo que ningún analizador estático puede ver, como cabeceras que faltan
- **Pasivo** (`zap-baseline`): rápido, inofensivo, apto para cada despliegue
- **Activo** (`zap-full-scan`): ataca de verdad, encuentra el XSS, solo en staging y con permiso
- Levanta la aplicación y ZAP en la misma red de Docker para que funcione en cualquier sistema
- Espera siempre a que la aplicación responda antes de escanear
- Gestiona los avisos con `rules.tsv` y ve subiendo el listón
