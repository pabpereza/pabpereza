# SBOM y firma de imágenes

Este capítulo responde a dos preguntas que parecen sencillas hasta que alguien nos las hace en serio:

1. **¿Qué hay exactamente dentro de esa imagen que tenemos en producción?**
2. **¿Cómo demostramos que es la que construyó nuestro pipeline y no otra?**

## Qué es un SBOM

Un **SBOM** (*Software Bill of Materials*, lista de materiales de software) es el inventario completo de todo lo que compone nuestro artefacto: cada paquete, cada versión y cada licencia.

La analogía es la etiqueta de ingredientes de un alimento. No evita que el producto lleve algo que no nos siente bien, pero sin ella no podemos ni saberlo.

Su utilidad real se ve el día que sale un Log4Shell. La pregunta que llega a las cuatro de la tarde es *"¿estamos afectados?"*, y con un SBOM se responde con un `grep` en lugar de con dos días de arqueología.

## Laboratorio: generar el SBOM

Usamos [Syft](https://github.com/anchore/syft):

```bash
cd devsecops-demo
docker build -t devsecops-demo:1.0 .

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  anchore/syft:latest devsecops-demo:1.0 -o spdx-json > sbom.json
```

Y ahora la pregunta interesante: ¿cuántos paquetes creemos que tiene una aplicación con **tres dependencias declaradas**?

```bash
python3 -c "import json; print(len(json.load(open('sbom.json'))['packages']))"
```

```
696
```

Seiscientos noventa y seis. Ahí está todo: nuestras tres dependencias, sus transitivas, los paquetes del sistema operativo de la imagen base y hasta el propio npm que viene dentro de `node:16`.

Esa cifra es el argumento entero del capítulo. **No podemos responder a "¿estamos afectados?" sobre 696 paquetes de memoria.**

### Formatos

| Formato | Origen | Cuándo usarlo |
|---|---|---|
| **SPDX** | Linux Foundation, ISO | Cumplimiento normativo y licencias |
| **CycloneDX** | OWASP | Seguridad y análisis de vulnerabilidades |

Syft genera ambos (`-o spdx-json`, `-o cyclonedx-json`). Si no tenemos un motivo para elegir, CycloneDX encaja mejor con herramientas de seguridad.

### Un SBOM sirve para escanear

No es solo un inventario que se guarda. Podemos escanearlo sin tener la imagen delante:

```bash
docker run --rm -v "$PWD:/w" -w /w aquasec/trivy:latest sbom sbom.json
```

Esto es lo que permite responder a un CVE nuevo sobre imágenes que ya están desplegadas, sin reconstruir nada.

## Firmar la imagen

El SBOM dice qué hay dentro. La firma demuestra **quién la construyó y que no ha cambiado desde entonces**.

El problema que resuelve: entre que nuestro pipeline construye la imagen y que el cluster la ejecuta, hay un registry de por medio. Si alguien compromete el registry y sustituye la imagen manteniendo la etiqueta, nosotros no nos enteramos. Las etiquetas son mutables; `demo:1.0` puede apuntar hoy a una cosa y mañana a otra.

Usamos [Cosign](https://docs.sigstore.dev/cosign/overview/), del proyecto Sigstore.

### Montar un registry local

```bash
docker run -d --rm -p 5001:5000 --name reg registry:2

docker tag devsecops-demo:1.0 localhost:5001/demo:1.0
docker push localhost:5001/demo:1.0
```

:::tip Por qué el puerto 5001

En macOS el 5000 lo ocupa AirPlay Receiver. Usar el 5001 evita un rato de desconcierto.

:::

### Generar el par de claves

```bash
export COSIGN_PASSWORD=""   # solo para el laboratorio

docker run --rm -e COSIGN_PASSWORD --network host -v "$PWD:/w" -w /w \
  gcr.io/projectsigstore/cosign:v2.4.1 generate-key-pair
```

```
Private key written to cosign.key
Public key written to cosign.pub
```

`cosign.key` es nuestra clave privada: nunca al repositorio. En un pipeline real va en un secreto, y en producción se usa **firma sin claves** (más abajo).

### Firmar y verificar

```bash
docker run --rm -e COSIGN_PASSWORD --network host -v "$PWD:/w" -w /w \
  gcr.io/projectsigstore/cosign:v2.4.1 \
  sign --key cosign.key --tlog-upload=false --yes localhost:5001/demo:1.0
```

```
Pushing signature to: localhost:5001/demo
```

La firma se guarda **en el propio registry**, como un artefacto más asociado al digest de la imagen. No hay que gestionar almacenamiento aparte.

Ahora la verificación:

```bash
docker run --rm -e COSIGN_PASSWORD --network host -v "$PWD:/w" -w /w \
  gcr.io/projectsigstore/cosign:v2.4.1 \
  verify --key cosign.pub --insecure-ignore-tlog=true localhost:5001/demo:1.0
```

```
Verification for localhost:5001/demo:1.0 --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - The signatures were verified against the specified public key

[{"critical":{"identity":{"docker-reference":"localhost:5001/demo"},
  "image":{"docker-manifest-digest":"sha256:6b778eae8638..."},
  "type":"cosign container image signature"}}]
```

Fijémonos en que lo que se firma es el **digest**, no la etiqueta. Ese `sha256:6b778...` identifica un contenido exacto e inmutable.

### Y ahora la parte que convence

Subimos otra imagen cualquiera con otra etiqueta, sin firmarla, e intentamos verificarla:

```bash
docker tag alpine:latest localhost:5001/demo:2.0
docker push localhost:5001/demo:2.0

docker run --rm -e COSIGN_PASSWORD --network host -v "$PWD:/w" -w /w \
  gcr.io/projectsigstore/cosign:v2.4.1 \
  verify --key cosign.pub --insecure-ignore-tlog=true localhost:5001/demo:2.0
```

```
Error: no signatures found
```

Eso es exactamente lo que queremos que pase en nuestro cluster antes de arrancar un contenedor.

:::warning Los flags del laboratorio

`--tlog-upload=false` e `--insecure-ignore-tlog=true` desactivan el registro de transparencia público, porque una imagen en `localhost` no debe acabar en un log público. **En producción no se usan**: el log de transparencia es una parte importante del modelo de seguridad de Sigstore.

Fijemos siempre la versión de cosign (aquí `v2.4.1`): estos flags han cambiado entre versiones recientes.

:::

## Firma sin claves

Gestionar claves privadas es la parte que sale mal. Sigstore permite firmar usando la identidad del pipeline (el token OIDC de GitHub Actions), sin claves de larga duración:

```yaml
- uses: sigstore/cosign-installer@v3

- name: Firmar
  run: cosign sign --yes ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}
  env:
    COSIGN_EXPERIMENTAL: 1
```

Requiere `permissions: id-token: write` en el job. La verificación pasa entonces a comprobar *quién* firmó:

```bash
cosign verify \
  --certificate-identity-regexp "https://github.com/pabpereza/.*" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  ghcr.io/pabpereza/demo:1.0
```

Traducido: *"acepto esta imagen solo si la firmó un workflow de GitHub Actions de mi organización"*. Sin claves que rotar ni que perder.

## Dónde se comprueba de verdad

Firmar no sirve de nada si nadie verifica. El sitio donde tiene efecto es la puerta de entrada del cluster: un *admission controller* que rechaza cualquier imagen sin firma válida.

Eso se hace con políticas de admisión en Kubernetes, y lo tenemos cubierto en el [capítulo de admission controllers del curso de Kubernetes](../kubernetes/404.Admission_controllers.md).

## Resumen

- Un SBOM es el inventario de todo lo que compone nuestro artefacto: **696 paquetes** para tres dependencias declaradas
- Sirve para responder a "¿estamos afectados?" con un `grep` en vez de con arqueología
- La firma demuestra origen e integridad, y se guarda en el propio registry
- Se firma el **digest**, no la etiqueta, porque las etiquetas son mutables
- Verificar una imagen sin firma falla con `no signatures found`, que es justo lo que queremos
- En producción: firma sin claves con la identidad del pipeline, y verificación en el admission controller
