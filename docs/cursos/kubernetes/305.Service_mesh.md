# Service mesh en Kubernetes

A medida que una arquitectura de microservicios crece, aparecen necesidades que se repiten en **cada** servicio: cifrar el tráfico entre pods, reintentar peticiones fallidas, medir latencias, hacer canary releases... Podemos implementarlo en el código de cada aplicación (cincuenta veces), o podemos delegarlo en la plataforma. Esa segunda opción es el **service mesh**.

## ¿Qué es un service mesh?
Un service mesh es una capa de infraestructura que gestiona la **comunicación entre servicios**: interceptar todo el tráfico este-oeste (pod a pod) y aplicarle seguridad, fiabilidad y observabilidad de forma transparente, sin tocar el código de las aplicaciones.

Se compone de dos planos:
- **Data plane**: los proxies que interceptan el tráfico de cada pod (clásicamente, sidecars como Envoy).
- **Control plane**: el cerebro que configura todos esos proxies (Istiod en Istio, el controlador de Linkerd).

```mermaid
flowchart TD
    CP[Control plane<br/>configura los proxies]
    subgraph PodA [Pod app-a]
        A[app-a] --- PA[proxy]
    end
    subgraph PodB [Pod app-b]
        B[app-b] --- PB[proxy]
    end
    PA == mTLS ==> PB
    CP -.-> PA
    CP -.-> PB
```

¿Nos suena el patrón? Es el [sidecar](./302.Multicontainer_sidecars.md) llevado al extremo: el mesh **inyecta automáticamente** un proxy en cada pod (normalmente con un mutating admission webhook al etiquetar el namespace), y la app habla con el mundo sin saber que todo pasa por él.

## Qué nos da un service mesh
- **mTLS automático**: todo el tráfico entre pods se cifra y autentica mutuamente, con certificados rotados por el mesh. Es la implementación práctica del *zero trust* dentro del cluster (y complementa a las [NetworkPolicies](./118.Seguridad_network_policies.md): estas deciden *quién puede hablar con quién*, el mesh asegura *cómo* hablan).
- **Gestión de tráfico**: reintentos, timeouts, circuit breaking y repartos por porcentaje mucho más finos que los de un Service. Los [canary](./303.Canary_bluegreen.md) con métricas automáticas suelen apoyarse en un mesh.
- **Observabilidad**: métricas uniformes (latencia, tasa de error, throughput) y trazas distribuidas de **todos** los servicios sin instrumentar el código.
- **Políticas de autorización**: reglas del tipo "solo `frontend` puede llamar al `POST /pagos` de `backend`", a nivel de identidad de servicio, no de IP.

## Los actores: Istio y Linkerd
- **[Istio](https://istio.io/)**: el más completo y extendido. Usa Envoy como proxy y se configura con CRDs propias (`VirtualService`, `DestinationRule`, `Gateway`, `AuthorizationPolicy`). Su potencia tiene precio: complejidad operativa.
- **[Linkerd](https://linkerd.io/)**: la alternativa ligera, proyecto graduado de la CNCF. Filosofía minimalista: mTLS, métricas y reintentos con configuración casi nula y un proxy propio ultraligero en Rust.

> **Tendencia actual**: el modelo de un sidecar por pod está evolucionando. **Istio ambient mesh** elimina los sidecars (proxies a nivel de nodo) y **Cilium Service Mesh** usa eBPF en el kernel. El concepto que aprendemos aquí no cambia: solo la pieza que intercepta el tráfico.

## Ejemplo: probando Linkerd
Para que veamos lo tangible que es, el ciclo completo con Linkerd en un cluster de pruebas:

```bash
# Instalar la CLI y el mesh
curl -sL https://run.linkerd.io/install | sh
linkerd install --crds | kubectl apply -f -
linkerd install | kubectl apply -f -
linkerd check

# "Meshear" un namespace: la anotación hace que se inyecte el proxy
kubectl annotate namespace default linkerd.io/inject=enabled

# Reiniciar los deployments para que los pods renazcan con su sidecar
kubectl rollout restart deployment

# Ver el tráfico en vivo (con la extensión viz instalada)
linkerd viz stat deployments
```

A partir de ahí, todo el tráfico entre nuestros pods va cifrado con mTLS y tenemos métricas doradas de cada servicio. Sin tocar una línea de código.

En Istio, el equivalente sería `istioctl install`, etiquetar el namespace con `istio-injection=enabled` y configurar el tráfico con sus CRDs. Por ejemplo, un reparto canary 90/10 con `VirtualService`:

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: myapp
spec:
  hosts:
  - myapp
  http:
  - route:
    - destination:
        host: myapp
        subset: v1
      weight: 90
    - destination:
        host: myapp
        subset: v2
      weight: 10
```

## Istio en la práctica: cuatro sorpresas

En el curso presencial metimos Istio en un clúster que ya tenía ingress-nginx y aplicaciones funcionando. Esto es lo que no cuentan los tutoriales de "instálalo en cinco minutos".

### 1. El sidecar ya no está en `containers`

Con Kubernetes 1.29 o superior, las versiones recientes de Istio inyectan el proxy como **sidecar nativo**: un contenedor en **`initContainers`** con `restartPolicy: Always`, que arranca antes que la aplicación y sigue vivo mientras ella corre (lo vimos en [sidecars](./302.Multicontainer_sidecars.md)). Si lo buscamos en `spec.containers`, no aparece:

```bash
kubectl get pod <pod> -o jsonpath='{.spec.initContainers[*].name}{"\n"}'   # istio-proxy
kubectl logs <pod> -c istio-proxy                                          # sus logs, igual que siempre
```

`kubectl get pods` sigue mostrando `2/2` en `READY`, porque cuenta los sidecars nativos.

### 2. Los nombres de los puertos importan

Istio necesita saber **qué protocolo** va por cada puerto del Service. Lo deduce del nombre (`http`, `http-web`, `grpc`, `tcp-postgres`...) o del campo `appProtocol`. Si no lo encuentra, intenta adivinarlo mirando el tráfico, y con protocolos en los que habla primero el servidor (PostgreSQL, MySQL, Redis...) la adivinanza falla. Nombremos siempre los puertos:

```yaml
  ports:
    - name: http-api        # Istio lo tratará como HTTP
      port: 80
      targetPort: 8000
    - name: tcp-postgres    # y este, como TCP a secas
      port: 5432
```

### 3. `STRICT` rompe la entrada desde ingress-nginx

Con una `PeerAuthentication` en modo **`STRICT`**, los pods del mesh **solo aceptan mTLS**. Pero los pods de ingress-nginx **no están en el mesh**: mandan HTTP en claro, el sidecar del destino lo rechaza y desde fuera vemos errores `502`. Desde dentro del mesh, en cambio, todo funciona, así que despista.

Hay tres salidas:
- Dejar el modo **`PERMISSIVE`** (acepta mTLS y texto plano) mientras convivan los dos mundos.
- Abrir solo el puerto de entrada con `portLevelMtls` en `PERMISSIVE` y dejar el resto en `STRICT`.
- Meter el controlador de entrada en el mesh, o usar el gateway de entrada del propio Istio.

### 4. Kiali necesita Prometheus

**Kiali**, la consola que dibuja el grafo de servicios, no recoge métricas: las **lee de Prometheus**. Sin él, Kiali arranca, pero el grafo sale vacío y se queja de que no puede conectar. Los dos vienen como complementos de ejemplo en la descarga de Istio:

```bash
kubectl apply -f istio-<versión>/samples/addons/prometheus.yaml
kubectl apply -f istio-<versión>/samples/addons/kiali.yaml
istioctl dashboard kiali
```

Y el grafo solo dibuja **tráfico reciente**: si no hay peticiones circulando, también saldrá vacío.

## ¿Necesitamos un service mesh?
La pregunta incómoda. Un mesh añade proxies en cada pod (latencia y consumo), CRDs nuevas y una pieza más que operar y actualizar. La regla práctica:

- **Probablemente no**, si tenemos pocos servicios, un solo equipo, y nuestras necesidades se cubren con Services, Ingress/Gateway API y NetworkPolicies.
- **Probablemente sí**, si tenemos decenas de microservicios y varios equipos, necesitamos mTLS y políticas de autorización entre servicios por cumplimiento, u observabilidad uniforme sin reinstrumentar todo.

Para el examen CKAD basta con el concepto: qué es, qué aporta (mTLS, tráfico, observabilidad), y que se implementa con proxies inyectados como sidecars configurados por un control plane.

## Resumen
- Un service mesh saca del código la seguridad, fiabilidad y observabilidad de la comunicación entre servicios.
- Data plane (proxies junto a cada pod) + control plane (que los configura). El patrón sidecar, automatizado.
- mTLS automático, gestión fina de tráfico, métricas y trazas uniformes, políticas de autorización por identidad.
- Istio = potencia y complejidad; Linkerd = simplicidad CNCF. Las arquitecturas sin sidecar (ambient, eBPF) son la evolución.
- No es obligatorio: adoptémoslo cuando el número de servicios y los requisitos lo justifiquen.
