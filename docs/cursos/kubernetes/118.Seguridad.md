# Seguridad en Kubernetes

La seguridad en Kubernetes es un tema muy amplio. En este capítulo veremos los fundamentos con ejemplos y ejercicios que podemos lanzar en nuestro propio clúster. Luego los ampliaremos en la especialización CKS del curso.

La agruparemos en cuatro bloques:
* **Accesos e identidades**: quién eres y qué puedes hacer (autenticación y autorización).
* **Security Context**: con qué privilegios se ejecuta cada contenedor.
* **Pod Security Admission**: qué pods se dejan entrar en cada namespace.
* **Network Policies**: quién puede hablar con quién.

Antes de entrar en materia, conviene conocer el modelo de las **4C** de la seguridad *cloud native*. Son cuatro capas, cada una dentro de la anterior, como unas muñecas rusas:

| Capa | Qué protege | Ejemplo |
|---|---|---|
| **C**loud | La infraestructura | Firewalls del proveedor, acceso a las máquinas |
| **C**luster | Kubernetes | RBAC, Pod Security, NetworkPolicies (este capítulo) |
| **C**ontainer | Las imágenes y su ejecución | Usuario no root, imágenes mínimas |
| **C**ode | Nuestra aplicación | Dependencias, secretos, validación de entradas |

De poco sirve un código perfecto si cualquiera puede entrar al clúster, y viceversa.

## Preparar el laboratorio

Todos los ejercicios del capítulo usan un namespace propio, así que al final basta con borrarlo:

```bash
kubectl create namespace seguridad
```

> Los ejercicios de NetworkPolicies necesitan un plugin de red (CNI) que las soporte, como Cilium o Calico. Con Flannel a secas se ignoran sin avisar.

## Autenticación, autorización y control de admisión

Cada petición a la API de Kubernetes pasa por tres controles, en este orden. Una buena analogía es el control de un aeropuerto:

1. **Autenticación**: ¿quién eres? Es enseñar el DNI.
2. **Autorización**: ¿puedes hacer esto? Es la tarjeta de embarque: estás identificado, pero solo puedes subir a tu avión.
3. **Control de admisión**: ¿lo que llevas cumple las normas? Es el escáner del equipaje: puede rechazar la petición o incluso modificarla antes de guardarla en etcd.

![Diagrama de autenticación, autorización y control de admisión](https://kubernetes.io/images/docs/admin/access-control-overview.svg)

### Autenticación

Kubernetes no tiene una base de datos de usuarios. Identifica a quien llama por sus credenciales: certificados x509, tokens, OpenID Connect (OIDC)... Lo veremos a fondo en el capítulo de [usuarios](./119.Usuarios.md).

### Autorización

Una vez identificados, Kubernetes decide si podemos hacer lo que pedimos. El modo estándar es **RBAC** (*Role Based Access Control*, control de acceso basado en roles): definimos roles con permisos y se los asignamos a usuarios, grupos o ServiceAccounts.

Los permisos se definen como **verbos** (`get`, `list`, `create`, `delete`...) sobre **recursos** (`pods`, `secrets`...). Así aplicamos el **principio de mínimo privilegio**: cada identidad tiene solo los permisos que necesita, ni uno más. Lo profundizaremos en el capítulo de [RBAC](./120.Roles.md).

### Control de admisión

Los *admission controllers* interceptan la petición después de autorizarla y antes de guardarla. Pueden **validarla** (rechazarla si no cumple una norma) o **mutarla** (modificarla, por ejemplo añadiendo valores por defecto, como hacen los LimitRange).

### Ejercicio 1: ¿quién soy y qué puedo hacer?

Pregúntale a Kubernetes con qué identidad estás trabajando:

```bash
kubectl auth whoami
```

```text
Username   kubernetes-admin
Groups     [kubeadm:cluster-admins system:authenticated]
```

Ahora, ¿qué puede hacer la ServiceAccount `default`, la que usan los pods si no indicamos otra? `--as` permite hacerse pasar por otra identidad:

```bash
kubectl auth can-i create pods --as=system:serviceaccount:default:default
kubectl auth can-i --list --as=system:serviceaccount:default:default
```

```text
no
```

La lista solo muestra unos pocos permisos básicos, como preguntar por los suyos propios. **Por defecto, un pod no puede tocar la API.**

Por último, en el control plane, mira qué modos de autorización y qué *admission controllers* tiene activados el API server:

```bash
sudo grep -E "authorization-mode|admission-plugins" /etc/kubernetes/manifests/kube-apiserver.yaml
```

```text
    - --authorization-mode=Node,RBAC
    - --enable-admission-plugins=NodeRestriction
```

Además de los que se activan aquí, hay varios que vienen activados por defecto, entre ellos el de Pod Security que veremos más adelante. En la especialización CKS veremos los [admission controllers en profundidad](./404.Admission_controllers.md).

> **Truco de examen:** `kubectl auth can-i` con `--as` es la forma más rápida de comprobar un permiso sin tener que crear credenciales.

## Security Context

El `securityContext` define **con qué privilegios se ejecuta** un contenedor: con qué usuario, si puede escalar privilegios, qué capacidades del kernel tiene o si puede escribir en su sistema de ficheros.

Se puede definir a nivel de **pod** (afecta a todos sus contenedores) y a nivel de **contenedor**. Si ambos definen el mismo campo, gana el del contenedor.

Los campos más importantes:

| Campo | Qué hace |
|---|---|
| `runAsUser` / `runAsGroup` | UID y GID con los que se ejecuta el proceso |
| `runAsNonRoot` | Impide arrancar si el contenedor fuera a ejecutarse como root |
| `fsGroup` | Grupo propietario de los volúmenes montados |
| `allowPrivilegeEscalation` | Impide que el proceso gane más privilegios que su padre (bloquea binarios como `sudo`) |
| `readOnlyRootFilesystem` | Sistema de ficheros raíz en solo lectura |
| `capabilities` | Añade o quita capacidades del kernel de Linux. Buena práctica: `drop: ["ALL"]` y añadir solo las imprescindibles |
| `privileged` | Acceso completo al host. Es una de las principales vías de escape de contenedores: evitémoslo siempre que podamos |
| `seccompProfile` | Filtro de llamadas al sistema. `RuntimeDefault` aplica el perfil por defecto del runtime |

### Ejercicio 2: por defecto, root

Lanza un contenedor sin ninguna configuración de seguridad y pregúntale quién es:

```bash
kubectl -n seguridad run curioso --rm -i --restart=Never --image=busybox:1.36 -- \
  sh -c 'id; touch /fichero && echo "puedo escribir en /"'
```

```text
uid=0(root) gid=0(root) groups=0(root),10(wheel)
puedo escribir en /
```

**Root y escribiendo donde quiere.** Es el punto de partida de casi todas las imágenes.

### Ejercicio 3: un pod endurecido

Guarda esto como `seguro.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: seguro
  namespace: seguridad
spec:
  securityContext:              # a nivel de pod
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  volumes:
    - name: tmp
      emptyDir: {}
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      securityContext:          # a nivel de contenedor
        runAsNonRoot: true
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: tmp             # un sitio donde sí se puede escribir
          mountPath: /tmp
```

```bash
kubectl apply -f seguro.yaml
```

Ahora comprueba cada medida por separado:

```bash
kubectl -n seguridad exec seguro -- id
```

```text
uid=1000 gid=3000 groups=2000,3000
```

El usuario 1000, el grupo 3000 y el grupo extra 2000 del `fsGroup`.

```bash
kubectl -n seguridad exec seguro -- touch /fichero
```

```text
touch: /fichero: Read-only file system
```

```bash
kubectl -n seguridad exec seguro -- sh -c 'touch /tmp/ok && ls -ln /tmp'
```

```text
-rw-r--r--    1 1000     2000             0 Oct 18 16:34 ok
```

En `/tmp` sí puede escribir, porque es un volumen, y el fichero pertenece al grupo 2000 del `fsGroup`.

```bash
kubectl -n seguridad exec seguro -- grep Cap /proc/1/status
```

```text
CapInh:	0000000000000000
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000000
CapAmb:	0000000000000000
```

Ceros: **ninguna capacidad del kernel**.

### Ejercicio 4: las capabilities, en acción

Root puede cambiar el propietario de un fichero gracias a la capacidad `CHOWN`. Compruébalo con y sin capabilities:

```bash
kubectl -n seguridad run con-caps --rm -i --restart=Never --image=busybox:1.36 -- \
  chown 1000 /etc/hostname
```

No dice nada: ha funcionado. Ahora el mismo comando quitando todas las capacidades. `kubectl run` no tiene una opción para el `securityContext`, así que se lo pasamos con `--overrides`:

```bash
kubectl -n seguridad run sin-caps --rm -i --restart=Never --image=busybox:1.36 \
  --overrides='{"spec":{"containers":[{"name":"sin-caps","image":"busybox:1.36","command":["chown","1000","/etc/hostname"],"securityContext":{"capabilities":{"drop":["ALL"]}}}]}}'
```

```text
chown: /etc/hostname: Operation not permitted
```

**Sigue siendo root, pero un root sin poderes.** Esa es la idea de `drop: ["ALL"]`.

### Ejercicio 5: cuando la imagen no colabora

`runAsNonRoot: true` no cambia el usuario: solo **comprueba** que no sea root. Prueba con la imagen oficial de nginx, que arranca como root:

```bash
kubectl -n seguridad run nginx-nonroot --image=nginx:alpine \
  --overrides='{"spec":{"containers":[{"name":"nginx-nonroot","image":"nginx:alpine","securityContext":{"runAsNonRoot":true}}]}}'
kubectl -n seguridad get pod nginx-nonroot
```

```text
NAME            READY   STATUS                       RESTARTS   AGE
nginx-nonroot   0/1     CreateContainerConfigError   0          15s
```

¿Por qué? Los eventos lo dicen claro:

```bash
kubectl -n seguridad describe pod nginx-nonroot
```

```text
Error: container has runAsNonRoot and image will run as root
```

**Pregunta:** ¿cómo lo arreglarías?

<details>
<summary>Solución</summary>

Hay dos caminos:

- **Usar una imagen preparada** para no ser root, como `nginxinc/nginx-unprivileged`, que escucha en el puerto 8080.
- **Indicar un usuario** con `runAsUser`. Con nginx normal no basta: necesita root para el puerto 80 y para escribir en sus directorios. Por eso existe la versión *unprivileged*.

La lección: el `securityContext` no hace milagros. **La imagen tiene que estar pensada para ejecutarse sin root.**

</details>

## Pod Security Standards y Pod Security Admission

Quizá nos suenen las **Pod Security Policies (PSP)**: permitían definir políticas de seguridad globales para todos los pods. Quedaron obsoletas en Kubernetes 1.21 y fueron **eliminadas en la 1.25**. Si nos las encontramos en un tutorial, es señal de que está desactualizado.

Su sustituto nativo es **Pod Security Admission (PSA)**, un admission controller integrado que aplica los **Pod Security Standards (PSS)**. Son tres niveles predefinidos:

| Nivel | Para qué | Qué bloquea, entre otras cosas |
|---|---|---|
| **privileged** | Cargas del sistema que de verdad lo necesitan | Nada |
| **baseline** | Aplicaciones normales, con mínima fricción | Contenedores privilegiados, `hostNetwork`, `hostPath`, añadir capacidades peligrosas |
| **restricted** | Lo más seguro | Todo lo anterior, y además obliga a `runAsNonRoot`, `allowPrivilegeEscalation: false`, `drop: ["ALL"]` y un `seccompProfile` |

Se aplica **etiquetando el namespace**, en tres modos que se pueden combinar:

| Modo | Qué hace con un pod que incumple |
|---|---|
| `enforce` | Lo **rechaza** |
| `warn` | Lo crea, pero **avisa** a quien lo crea |
| `audit` | Lo crea, y lo anota en el **log de auditoría** del clúster |

```bash
kubectl label namespace mi-app \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted
```

Esta combinación es la forma habitual de endurecer poco a poco: **bloqueamos lo grave y nos avisa de lo que nos falta** para llegar a `restricted`.

### Ejercicio 6: un namespace estricto

Crea un namespace con el nivel `restricted` en modo `enforce` e intenta lanzar un nginx normal:

```bash
kubectl create namespace seguridad-psa
kubectl label namespace seguridad-psa pod-security.kubernetes.io/enforce=restricted
kubectl -n seguridad-psa run nginx --image=nginx:alpine
```

```text
Error from server (Forbidden): pods "nginx" is forbidden: violates PodSecurity "restricted:latest":
allowPrivilegeEscalation != false (container "nginx" must set securityContext.allowPrivilegeEscalation=false),
unrestricted capabilities (container "nginx" must set securityContext.capabilities.drop=["ALL"]),
runAsNonRoot != true (pod or container "nginx" must set securityContext.runAsNonRoot=true),
seccompProfile (pod or container "nginx" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
```

**Rechazado**, con la lista exacta de lo que falta. Es casi una receta.

Ahora cambia a `baseline` en `enforce` y deja `restricted` en `warn`:

```bash
kubectl label namespace seguridad-psa --overwrite \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/warn=restricted
kubectl -n seguridad-psa run nginx --image=nginx:alpine
```

```text
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false, ...
pod/nginx created
```

**Creado, pero con aviso.** ¿Y un contenedor privilegiado?

```bash
kubectl -n seguridad-psa run privi --image=busybox:1.36 \
  --overrides='{"spec":{"containers":[{"name":"privi","image":"busybox:1.36","command":["sleep","3600"],"securityContext":{"privileged":true}}]}}'
```

```text
Error from server (Forbidden): pods "privi" is forbidden: violates PodSecurity "baseline:latest":
privileged (container "privi" must not set securityContext.privileged=true)
```

Eso ya lo bloquea `baseline`.

### Ejercicio 7: un pod que cumple `restricted`

Vuelve a poner el namespace en `restricted`. Escribe un pod de `busybox` que **cumpla** ese nivel y compruébalo.

```bash
kubectl label namespace seguridad-psa --overwrite pod-security.kubernetes.io/enforce=restricted
```

<details>
<summary>Solución</summary>

Basta con seguir la lista del error del ejercicio 6:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: cumple
  namespace: seguridad-psa
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
```

```bash
kubectl apply -f cumple.yaml
kubectl -n seguridad-psa get pod cumple
```

Arranca sin errores. Fíjate en que, al cambiar la etiqueta del namespace, Kubernetes avisa de los pods que **ya existían** y no cumplen (el `nginx` de antes): no los borra, pero te lo dice.

</details>

> **Truco antes de endurecer un namespace en producción:** `--dry-run=server` te dice qué pods existentes incumplirían el nivel, sin cambiar nada:
> ```bash
> kubectl label --dry-run=server --overwrite namespace mi-app \
>   pod-security.kubernetes.io/enforce=restricted
> ```

Para necesidades más avanzadas (políticas a medida, mutación), se usan motores de políticas como **OPA Gatekeeper** o **Kyverno**, que veremos en la [especialización CKS](./407.OPA.md).

## Network Policies

Por defecto, **cualquier pod puede hablar con cualquier otro**, esté en el namespace que esté. Una NetworkPolicy es como el portero de una discoteca: decide quién entra (`Ingress`) y adónde puede ir cada uno (`Egress`).

La regla de oro: en cuanto una política **selecciona** a un pod, todo el tráfico del tipo indicado queda **denegado** para ese pod, salvo lo que la política permita expresamente. Y las políticas **se suman**: si dos políticas seleccionan al mismo pod, vale lo que permita cualquiera de ellas.

### Ejercicio 8: el portero de la web

Prepara una web y dos clientes: uno con la etiqueta `rol=cliente` y otro sin ella.

```bash
kubectl -n seguridad run web --image=nginx:alpine --labels=app=web --expose --port=80
kubectl -n seguridad run cliente --image=busybox:1.36 --labels=rol=cliente -- sleep 3600
kubectl -n seguridad run intruso --image=busybox:1.36 -- sleep 3600
```

Una forma rápida de probar los dos a la vez:

```bash
for p in cliente intruso; do
  echo -n "$p -> web: "
  kubectl -n seguridad exec $p -- wget -qO- -T3 http://web > /dev/null 2>&1 && echo OK || echo BLOQUEADO
done
```

```text
cliente -> web: OK
intruso -> web: OK
```

**Paso 1. Cerrar la puerta a todo.** `podSelector: {}` selecciona todos los pods del namespace, y sin reglas de `ingress` no se permite nada:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: seguridad
spec:
  podSelector: {}
  policyTypes:
    - Ingress
```

Aplícala y repite la prueba: **los dos bloqueados**.

**Paso 2. Dejar pasar solo a los clientes:**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-solo-clientes
  namespace: seguridad
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              rol: cliente
      ports:
        - protocol: TCP
          port: 80
```

```text
cliente -> web: OK
intruso -> web: BLOQUEADO
```

**Paso 3. El intruso se disfraza.** ¿Qué pasa si alguien le pone la etiqueta?

```bash
kubectl -n seguridad label pod intruso rol=cliente
```

```text
cliente -> web: OK
intruso -> web: OK
```

**Pasa.** Las NetworkPolicies confían en las **etiquetas**, así que quien puede etiquetar pods puede saltárselas. Por eso los permisos sobre pods (RBAC) y las políticas de red van de la mano. Quítale la etiqueta antes de seguir:

```bash
kubectl -n seguridad label pod intruso rol-
```

### Ejercicio 9: cerrar la salida (y no romper el DNS)

Deniega también todo el tráfico de **salida** del namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: seguridad
spec:
  podSelector: {}
  policyTypes:
    - Egress
```

Prueba desde el cliente:

```bash
kubectl -n seguridad exec cliente -- wget -qO- -T3 http://web
```

```text
wget: bad address 'web'
```

Fíjate en el error: no es que la web no responda, es que **ya ni siquiera resuelve el nombre**. Al cerrar la salida, hemos cerrado también el camino hacia el DNS del clúster.

**Pregunta:** escribe una política que permita al cliente usar el DNS y llegar a la web, y nada más.

<details>
<summary>Solución</summary>

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: permitir-dns-y-web
  namespace: seguridad
spec:
  podSelector:
    matchLabels:
      rol: cliente
  policyTypes:
    - Egress
  egress:
    - to:                                   # el DNS del clúster
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
    - to:                                   # la web
        - podSelector:
            matchLabels:
              app: web
      ports:
        - protocol: TCP
          port: 80
```

```text
cliente -> web: OK
intruso -> web: BLOQUEADO
```

Y hacia internet, el cliente sigue **bloqueado**: solo puede ir a donde hemos dicho.

</details>

### La trampa del guion: AND frente a OR

Mira con atención estas dos reglas. Solo cambia un guion:

```yaml
# Regla A: UN elemento con dos selectores -> deben cumplirse LOS DOS (AND)
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            equipo: frontend
        podSelector:
          matchLabels:
            rol: cliente
```

```yaml
# Regla B: DOS elementos -> basta con cumplir UNO (OR)
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            equipo: frontend
      - podSelector:
          matchLabels:
            rol: cliente
```

- **Regla A:** pods con `rol=cliente` **que estén en** namespaces con `equipo=frontend`.
- **Regla B:** **cualquier** pod de los namespaces `equipo=frontend`, **o** los pods con `rol=cliente` del namespace de la política.

Es uno de los errores más comunes, y una pregunta clásica de examen.

### Un ejemplo completo

Para terminar, una política que combina todo: entrada desde un rango de IPs (con una excepción), desde un namespace y desde unos pods concretos, y salida solo hacia un rango y un puerto.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ingress-egress-policy
  namespace: default
spec:
  podSelector:
    matchLabels:
      role: db
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - ipBlock:
            cidr: 172.17.0.0/16
            except:
              - 172.17.1.0/24
        - namespaceSelector:
            matchLabels:
              project: myproject
        - podSelector:
            matchLabels:
              role: frontend
      ports:
        - protocol: TCP
          port: 6379
  egress:
    - to:
        - ipBlock:
            cidr: 10.0.0.0/24
      ports:
        - protocol: TCP
          port: 5978
```

Con lo visto en la trampa del guion: los tres orígenes de `from` son elementos **distintos**, así que basta con cumplir **uno**.

Veremos patrones más avanzados en la [especialización CKS](./403.Network_policies_avanzadas.md).

## Resumen

- Toda petición a la API pasa por **autenticación**, **autorización** (RBAC) y **control de admisión**. `kubectl auth can-i --as` comprueba permisos sin crear credenciales.
- El **securityContext** limita los privilegios de cada contenedor: usuario no root, sin escalada de privilegios, sin capacidades y sistema de ficheros en solo lectura. Pero **la imagen tiene que colaborar**.
- Las **Pod Security Policies ya no existen**. El mecanismo actual es **Pod Security Admission**, por namespace: `enforce` para bloquear, `warn` y `audit` para avisar. `baseline` en `enforce` y `restricted` en `warn` es un buen punto de partida.
- Sin **NetworkPolicies**, todo el tráfico está permitido. Al cerrar la salida, **acuérdate del DNS**. Y vigila el guion: un elemento con dos selectores es AND; dos elementos son OR.
