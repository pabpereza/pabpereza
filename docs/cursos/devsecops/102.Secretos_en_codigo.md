# Secretos en el código

Empezamos por aquí porque es el fallo más común, el más fácil de cometer y el que más rápido se explota. Un token de AWS publicado en un repositorio público se encuentra y se usa en cuestión de minutos: hay bots dedicados exclusivamente a eso.

Y no hace falta ser descuidado. Basta con un `console.log` de depuración, un fichero de configuración que se coló en el commit o un "lo pongo aquí temporalmente" de hace dos años.

## Por qué borrar la línea no arregla nada

Este es el punto que casi todo el mundo descubre tarde.

Git guarda **todo el historial**. Si escribimos una contraseña, hacemos commit, nos damos cuenta y la borramos en el commit siguiente, la contraseña sigue ahí: en el primer commit, para siempre, accesible con un `git log -p`.

```
commit 1: añade API_KEY = "abc123"     ← el secreto vive aquí
commit 2: quita la API_KEY             ← esto no borra nada
```

Por eso el orden correcto al filtrar un secreto es siempre **rotar primero, limpiar después**. Volveremos a ello al final.

## Laboratorio: encontrar los secretos

Usamos [gitleaks](https://github.com/gitleaks/gitleaks), que escanea el historial completo buscando patrones conocidos y cadenas de alta entropía.

```bash
git clone https://github.com/pabpereza/devsecops-demo
cd devsecops-demo

docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest detect -s /repo -v
```

Tarda unos cuatro segundos. Salida real:

```
Finding:     secretAccessKey: 'bQ8xK2mNvR7wZ4tY6uH1sD3fG5jL0pA9cE7iO2nM'
RuleID:      generic-api-key
Entropy:     5.221928
File:        src/config.js
Line:        19
Commit:      d2cfcbaa96ee67dd3c9a3b891b35d01ad3eff674
Author:      pabpereza
Fingerprint: d2cfcbaa96ee67dd3c9a3b891b35d01ad3eff674:src/config.js:generic-api-key:19

WRN leaks found: 2
```

Fijémonos en lo que nos da, porque cada campo tiene su utilidad:

- **`RuleID`** — qué regla saltó. `generic-api-key` es la genérica; también hay reglas específicas para AWS, Stripe, Slack, GitHub y un par de cientos más.
- **`Entropy`** — cómo de "aleatoria" es la cadena. Un `password = "1234"` tiene entropía baja y probablemente sea un ejemplo; un 5.2 huele a credencial real.
- **`Commit`** y **`Author`** — cuándo entró y quién lo metió. Sin culpar a nadie: sirve para saber cuánto tiempo lleva expuesto.
- **`Fingerprint`** — el identificador que usaremos para silenciar un falso positivo.

El segundo hallazgo está en `infra/main.tf`: la contraseña de la base de datos escrita en el Terraform.

## Bloquearlo antes de que ocurra

Detectarlo está bien, pero lo que queremos es que no llegue a entrar. Para eso está `gitleaks protect`, que analiza lo que tenemos en el *staging area* antes de confirmarlo:

```bash
echo "const t = 'ghp_A9dK2mQxZvR3bTnW6yHpLcJ8sF4gN7eU1iO0';" > nuevo.js
git add nuevo.js

docker run --rm -v "$PWD:/repo" -w /repo zricethezav/gitleaks:latest protect --staged -v
```

```
RuleID:      github-pat
File:        nuevo.js
WRN leaks found: 1
```

Lo ha cazado antes del commit. Para automatizarlo, un hook de `pre-commit`:

```bash
# .git/hooks/pre-commit
#!/bin/sh
docker run --rm -v "$PWD:/repo" -w /repo \
  zricethezav/gitleaks:latest protect --staged || {
    echo "❌ Secreto detectado. Commit abortado."
    exit 1
  }
```

```bash
chmod +x .git/hooks/pre-commit
```

:::warning Un hook local no es un control de seguridad

Los hooks de `.git/hooks/` no se versionan, no se comparten y cualquiera puede saltárselos con `git commit --no-verify`. Sirven para **evitar el despiste**, que es su función. El control de verdad va en CI, donde nadie puede saltárselo.

:::

## GitHub ya nos está vigilando

Mientras preparaba el repositorio de este curso me pasó algo que ilustra el capítulo mejor que cualquier explicación: **GitHub se negó a aceptar el push**.

```
remote: —— Slack API Token ————————————————————————
remote:  locations:
remote:    - commit: 7f45da48a43bb...
remote:      path: src/config.js:27
remote: ! [remote rejected] main -> main (push declined due to repository rule violations)
```

Es la *push protection* de GitHub, activada por defecto en repositorios públicos. Detecta tokens de proveedores conocidos y **rechaza el push entero** antes de que el secreto llegue al servidor.

Es una red de seguridad excelente, pero tiene dos límites que conviene tener claros:

1. **Solo reconoce formatos de proveedores concretos.** En ese mismo push, la clave de AWS y la contraseña de Terraform pasaron sin problema. Nuestro `DB_PASSWORD=hunter2` también pasará.
2. **Solo cubre GitHub.** Si usamos GitLab, Bitbucket o un Git propio, no existe.

Por eso sigue haciendo falta gitleaks: cubre lo que el proveedor no cubre.

## En el pipeline

```yaml
# .github/workflows/secretos.yml
name: Secretos
on: [push, pull_request]

jobs:
  gitleaks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # sin esto solo se analiza el último commit
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

El `fetch-depth: 0` es importante: por defecto Actions clona solo el último commit, y entonces estaríamos analizando una parte mínima del historial.

## Falsos positivos

Van a aparecer: cadenas de ejemplo, datos de test, hashes. Se silencian con su fingerprint en un fichero `.gitleaksignore`:

```
d2cfcbaa96ee67dd3c9a3b891b35d01ad3eff674:src/config.js:generic-api-key:19
```

Seamos restrictivos. Silenciar un fichero entero es la forma más rápida de que el próximo secreto de verdad pase desapercibido.

## Qué hacer cuando ya se ha filtrado

En este orden, y el orden importa:

1. **Rotemos la credencial.** Ya. Antes de tocar el historial, antes de avisar a nadie. Mientras siga siendo válida, sigue siendo un problema.
2. **Revisemos los accesos.** Miremos los logs del proveedor por si se ha usado.
3. **Limpiemos el historial** con `git filter-repo` o el asistente de GitHub. Es lo último y lo menos urgente: si hemos rotado, el secreto del historial ya no vale nada.
4. **Pongamos el control** para que no vuelva a pasar. Ese es el paso que la gente se salta.

Asumamos siempre que un secreto publicado, aunque fuera un minuto, está comprometido.

## Resumen

- Git guarda el historial: borrar la línea no borra el secreto
- `gitleaks detect` analiza el historial; `gitleaks protect --staged` lo evita antes del commit
- El hook local evita despistes, pero el control real va en CI
- La push protection de GitHub ayuda, pero solo cubre formatos conocidos y solo en GitHub
- Ante una fuga: **rotar primero**, limpiar después
